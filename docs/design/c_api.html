CRuby 互換 C API（monoruby_capi/）

CRuby 向けに書かれた C 拡張を、ソースのまま monoruby 用にビルドして require できるようにする層。doc/native_extension_loading.md §4 の段階 5 （「必要なら A を mr_* の上に積む」）にあたる。設計検討の経緯は doc/c_extention.md（2026-08）。

1. 使い方

root=~/.monoruby/v<version>      # globals::install_root()
cc -shared -fPIC -I "$root/include" -o foo.so foo.c "$root/capi/capi.c"
monoruby -I . -e 'require "foo"; ...'
  • include/ に ruby.h、ruby/{ruby,intern,encoding,thread,version,…}.h と、その土台の monoruby_ext.h が入る（build.rs が monoruby_capi/include と monoruby_ext_sys/include から置く）。
  • capi/capi.c が rb_* の実装。拡張ごとに静的にリンクする（§3.1）。
  • できた .so は $LOAD_PATH 上の普通の require "foo" / require "x/foo" で読める。初期化関数は CRuby と同じ void Init_foo(void)。
  • CRuby 用にビルド済みの .so は読めない（§2）。読もうとすると LoadError（「monoruby’s C API headers でビルドせよ」）になる。

extconf.rb のある拡張は CRuby と同じ手順でビルドできる（§3.10）:

monoruby extconf.rb && make          # RbConfig が $root/include と
                                     # $root/capi/libmonoruby_capi.a を指す
monoruby "$root/bin/gem" install foo # C 拡張付き gem も同じ経路でビルド

gem install したものは monoruby 専用の gem home （~/.monoruby/gems/<api version>、Gem.default_dir）に入る。

2. 互換の範囲: API 互換、ABI 非互換

拡張の中の VALUE は CRuby のビット列（64-bit、flonum あり）で、 monoruby の Value（value.rs）とは層（capi.c）が境界で相互変換する （段階 8、§3.15）。

即値はヘッダのマクロに焼き込まれるので、CRuby のヘッダでビルドした .so はそれでも動かない（rb_* の実体が libruby ではなく層だから）。 必ず再コンパイルする。

拡張から見える CRuby との差:

  • オブジェクトレイアウトのマクロ（RSTRING_PTR、RARRAY_LEN、RBASIC …）は関数。RBasic / RString 構造体は無い。RARRAY_PTR / RARRAY_CONST_PTR は要素を変換したコピーを指し（§3.15）、読み取り 専用（書くときは rb_ary_store / RARRAY_ASET）。
  • 世代別 GC が無いので write barrier（RB_OBJ_WRITE 等）は代入だけ。

3. 設計

3.1 シムは拡張に静的リンクする

rb_* の実体は C で書いた capi.c で、各拡張の .so に一緒にリンク される。monoruby 本体は rb_* を一切 export しない。

  • rb_raise は longjmp、rb_funcall(recv, mid, n, ...) は可変長引数で、 どちらも Rust では素直に書けない（setjmp は Rust から呼べず、可変長の 定義は nightly 機能）。C で書くのが自然。
  • 本体から --export-dynamic で出す案は、テストバイナリを含む全バイナリの シンボル表を膨らませ、rb_* の ABI をコアに固定する。静的リンクなら .so は自己完結し、monoruby_ext.h の表（MrApi）だけが境界になる （native_extension_loading.md §4.3 の「拡張は monoruby をリンクしない」 をそのまま守る）。
  • 判別: ローダは dlsym(handle, "monoruby_capi_init") があれば C API 拡張 とみなし、monoruby_capi_init(ctx, Init_foo) を呼ぶ（ext.rs load_capi_extension）。$LOAD_PATH 上で見つかった .so は ext::is_capi_extension がファイルのシンボル表（ELF の .dynsym、 Mach-O の LC_SYMTAB）に monoruby_capi_init があるかで判定し、開かない （§3.18。dlopen で試すと、libruby.so をリンクした CRuby 用の .so は 開けてしまい、その依存ライブラリがプロセスに残る）。

3.2 フレームと例外

capi.c はスレッドごとに「現在のフレーム」capi_cur を持つ: MrContext*、渡されたブロック、jmp_buf、外側のフレーム。

  • Ruby → C の入口（capi_dispatch、monoruby_capi_init）と rb_protect がフレームを積み、setjmp する。
  • API 呼び出しが失敗すると（MR_UNDEF が返る / -1 が返る）、エラーは インタプリタ側に保留されたまま capi_unwind が一番内側のフレームへ longjmp する。越えるのは拡張自身の C フレームだけで、Rust / JIT の フレームは一切越えない（native_extension_loading.md §4.3 規則 2）。 capi_dispatch は MR_UNDEF を返し、保留中のエラーがそのまま Ruby の 例外になる。
  • rb_protect はエラーを error_take で例外オブジェクトとして取り出し rb_errinfo に置く。rb_jump_tag / rb_ensure / rb_rescue2 はこの上。 block からの return / break / throw などクラスを持たない大域脱出は、 error_take が種類ごと Exception のオブジェクトに包んで返し、 raise_exception（rb_jump_tag）がそれを元の脱出に戻す （psych の Psych.parse が block 内の return で抜ける）。
  • @ で始まらない名前の ivar（rb_iv_set(obj, "-aggregators", ...)、 CRuby の隠し ivar）は / を前に付けたコア側の隠し ivar になり、 #instance_variables や inspect には出ない。
  • Ruby を呼ぶ API（rb_funcall、rb_yield、rb_proc_call、 rb_thread_call_without_gvl）は戻ったあと capi_cur を呼ぶ前の値に戻す。 green thread の切り替えは LIFO でないので、呼び出し中に別スレッドが同じ OS スレッドで拡張に入っても自分のフレームが残る。

3.3 GC: 呼び出し中は全部生かす

CRuby は C スタックを保守的に走査するので、拡張はローカル変数の VALUE を気にせず rb_funcall を挟める。monoruby の GC は precise なので、層が C に渡すヒープ上の VALUE はすべて temp stack に積む（root()）。 temp stack はメソッド呼び出し（と Init_）が戻ったときにインタプリタが 切り詰める。TruffleRuby の ExtensionCallStack と同じ考え方 （doc/c_extention.md §3.4）。

呼び出しを越えて C のグローバル変数に持つ値は CRuby と同じく rb_gc_register_address / rb_global_variable（アドレスを毎回読む新しい ABI 項目 gc_register_address）か rb_gc_register_mark_object（pin）。

代償: 1 回の呼び出しの中で大量に値を作るループは、戻るまで全部生かす。

3.4 メソッド

rb_define_method(klass, name, func, argc) は capi_method { func, arity } を確保し、新しい ABI 項目 define_method_data で「capi_dispatch + そのポインタ」として登録する。capi_dispatch が arity（-2、-1、0〜15）に 応じて CRuby の呼び出し規約で func を呼ぶ。引数個数のチェックは固定 arity ならコア側の builtin と同じ。

rb_define_attr は Ruby の attr_reader / attr_writer を呼んだあと public にする（C から呼ぶと require された場所の既定の可視性、 トップレベルなら private を拾うため）。

3.5 文字列

RSTRING_PTR は新しい ABI 項目 str_cptr を呼ぶ: 共有中なら切り離し、 長さの直後（予備容量）に NUL を置き、code range のキャッシュを捨てて、 String 自身のバッファを返す。書き込み可能で、rb_str_new(NULL, n) して RSTRING_PTR に書く CRuby の定石がそのまま動く。String は動かない （non-moving）ので、リサイズされるか回収されるまで有効。 rb_str_resize / rb_str_set_len は str_resize、rb_str_cat は str_cat。

3.6 そのほか

  • ID は IdentId。rb_id2name は ID ごとに一度だけ複製した C 文字列を 返す（プロセスの寿命の間有効）。
  • rb_cObject などのグローバル変数は monoruby_capi_init が定数参照で 埋める。拡張の static は 1 プロセスに 1 つなので、テストハーネスの ように 1 プロセスで複数のインタプリタを作ると後のものが勝つ（Init_ はインタプリタごとに走る）。ネイティブ拡張全般の既知の制約 （native_extension_loading.md §6.2）。
  • rb_encoding は名前ごとの小さな記録。添字 0/1/2 は CRuby と同じく ASCII-8BIT / UTF-8 / US-ASCII。
  • rb_thread_call_without_gvl は call_blocking_ubf（1:1 モデルでは GVL を 外して呼んだカーネルスレッド上で、green では native pool のワーカーで実行）。 ubf は呼び出しの間 ThreadInner::blocking_ubf に記録され、そのスレッドへの Thread#wakeup / #raise / #kill（interrupt_blocking）と、main が ブロック中のシグナル（ポーリング点でそれを見たスレッドが呼ぶ）で 1 回だけ GVL を持ったまま呼ばれる（CRuby の rb_threadptr_interrupt と同じ）。 RUBY_UBF_IO は関数なしで、割り込みの SIGVTALRM がシステムコールを EINTR で切る（1:1 モデルのみ。green ではワーカーに送るシグナルがなく未対応）。 fixture は tests/capi/capi_nogvl.c。
  • 多くの関数は Ruby のメソッドを rb_funcall で呼ぶだけの薄い実装 （TruffleRuby の Truffle::CExt と同じ方針）。正しさ優先で、ホットな ものから順に ABI 側へ寄せる。

3.7 Data / TypedData と alloc 関数（段階 2）

Data / TypedData のオブジェクトは本体のネイティブオブジェクト （native_new、種別 data_ops）で、ペイロードは層の記録 capi_data { data, dmark, dfree, type }。ruby.h の struct RData / struct RTypedData はこの記録のビューなので、RDATA(obj)->data / DATA_PTR(obj) は lvalue として書ける。data_ops の mark は type->function.dmark（型無しなら dmark）を、free は dfree （RUBY_DEFAULT_FREE なら xfree）を呼んで記録を解放する。 dsize / dcompact は読まない（non-moving）。

alloc 関数はコアの alloc_func（fn(ClassId, &mut Globals) -> Value、 Executor 無し、エラー不可）から直接は呼べないので遅延する:

  1. rb_define_alloc_func(klass, f) は新しい ABI 項目 class_set_alloc で klass のインスタンスをネイティブオブジェクトにし（既定の alloc は 「ペイロード無しで作る」ext_alloc_func）、f を層の表に記録する。 Ruby で定義したサブクラスはコアの継承でそのまま同じになる。
  2. new / allocate / dup が作った空のインスタンスを、DATA_PTR / TypedData_Get_Struct / rb_check_typeddata / RTYPEDDATA_P が最初に 見たとき、クラス（と祖先）の alloc 関数を呼び、できたオブジェクトから 記録を native_take（解放せずに外す）で取り、native_set で本物に 付ける。CRuby で allocate が alloc 関数を呼ぶのと同じ結果になる。 initialize_copy の中の TypedData_Get_Struct(copy) もこれで埋まる。
  3. alloc 関数を登録していないクラスに Data_Wrap_Struct したときも その場で class_set_alloc する（klass == 0 の隠しオブジェクトは層の 匿名クラス）。インスタンスが既にあるクラスでやると JIT の ivar 配置の 前提が崩れるので、拡張の Init_ で済ませること。
  4. rb_undef_alloc_func は MR_ALLOC_UNDEF（new が 「allocator undefined for X」）。

rb_check_typeddata のエラー文（「wrong argument type X (expected Y)」、 nil / true / false / 型無し Data / 別の型名）と parent による型の継承は CRuby と同じ。

3.8 C 関数をブロックにする

rb_block_call / rb_proc_new / rb_iterate は、層の隠しクラス （Class.new(Object)、ネイティブ）のインスタンスに {func, arg, block} を 持たせ、その call(*args) を Method#to_proc で Proc にして渡す。 call の入口 block_dispatch は capi_dispatch と同じフレームを積み、 そのフレームのブロックを「作った時点のメソッドのブロック」（Proc に しておく）にするので、コールバック内の rb_yield は CRuby と同じく rb_block_call を呼んだメソッドのブロックに届く。rb_block_call の callback が NULL なら自分のブロックをそのまま渡す。

rb_iter_break / rb_iter_break_value は層の隠し例外クラス （Exception 直下なので Ruby 側の rescue に捕まらず、ensure は走る）を 投げ、rb_block_call / rb_iterate が受け止めて値を返す。

3.9 rb_call_super と Struct

rb_call_super は新しい ABI 項目 call_super: コンテキストのフレーム （この C メソッド自身の lfp）の FuncId と名前、self のクラスから Store::check_super で次の定義を引き、invoke_func_named で呼ぶ。 ブロックは呼び出し元のものを渡す（CRuby の rb_call_super と同じ）。 メソッドの外（Init_）では RuntimeError。

rb_struct_define / rb_struct_define_under は Struct.new に、 rb_struct_new / aref / aset / getmember / members / size は それぞれの Ruby メソッドに委ねる。rb_obj_call_init は private の initialize をブロック付きで、rb_class_new / rb_module_new は Class.new / Module.new。

3.10 mkmf / gem install（段階 3）

CRuby の extconf.rb は mkmf が RbConfig から得る値だけでビルドを 組み立てる: ヘッダの場所（rubyhdrdir / rubyarchhdrdir）、コンパイラと フラグ、そして拡張がリンクする「libruby」（LIBRUBYARG）。vendored の rbconfig.rb はスナップショット元の CRuby の値を答えるので、そのままでは CRuby のヘッダでビルドした（monoruby では読めない）.so ができる。 builtins/capi_config.rb（startup.rb の最後に読む）が RbConfig.fire_update! でこれらを monoruby のものに差し替える:

  • gem home は monoruby 専用（stdlib/rubygems/defaults/operating_system.rb、 rubygems が $LOAD_PATH から読む packager 向けフック）。Gem.default_dir は ~/.monoruby/gems/<api version>、Gem.user_dir は ~/.local/share/gem/monoruby/<api version>。rubygems はビルド済み拡張を extensions/<platform>/<api version>/<gem> だけで区別するので、ホスト CRuby の gem home に入れると同じ gem の CRuby ビルドと上書きし合う。 ホストの gem ディレクトリは従来どおり GEM_PATH（Gem.path）に残り、 default gem の spec（Gem.default_specifications_dir）もホストのまま。
  • require の gem フォールバック: monoruby の require はホストの gem の lib/ をプローブ結果から知っているが、monoruby 自身の gem home に入った gem は知らない。$LOAD_PATH にもそこにも無いときに Gem.try_activate(feature)（rubygems の Kernel#require が LoadError で行うこと）を呼び、activate されたら探し直す （Executor::activate_gem_for）。rubygems の起動中・相対 / 絶対パス・ --disable-gems では呼ばない。
  • <install root>/bin/gem（bin/dist では bin/gem）は CRuby の bin/gem そのもの。monoruby "$root/bin/gem" install foo で使う。
  • tests/mkmf.rs: tests/capi/capi_gem/（extconf.rb 付きの gem）を extconf.rb + make でビルドする。gem build + gem install で monoruby と ホスト CRuby の双方にインストールし同じスクリプトの出力が一致することを 見る検査（と §3.24 のホスト gem の再ビルド検査）は bin/test-gems （bin/test が呼ぶシェルスクリプト。cargo test ではない）に移した： ホストの gem と gem cache、cc、make に依存し、開発機では処理系の外の 理由でよく落ちたため。

3.11 実 gem で面積を詰める（段階 4）

gem install でビルドした実 gem を CRuby と比較して足りない API を埋めた。 bin/test-gems（もと tests/capi_gems.rs。bin/test が呼ぶシェルスクリプトで、 cargo test からは外した）がホスト CRuby の gem cache にある .gem を monoruby の bin/gem で専用 home に入れ、tests/capi/gems/<gem>.rb を双方で走らせて 出力を比べる（1 行目は読み込んだ拡張の名前なので、stand-in でなく C 拡張が 動いたことも見る）。cache に .gem が無い gem はスキップとして報告する。

3.12 st_table（段階 5）

ruby/st.h の中身を入れた。実装は CRuby の st.c（public domain、 ruby_4_0 ブランチ）をそのまま monoruby_capi/src/st.c に持ち込んだもので、 Ruby 内部ヘッダへの依存（internal/bits.h の nlz_intptr、RUBY_ASSERT、 NO_SANITIZE）を冒頭の数行で置き換え、RHASH に入り込む rb_hash_bulk_insert_into_st_table とその裏の rehash 補助、内部用の set_table を落としただけ。st.h も CRuby の宣言と struct st_table の レイアウトをそのまま持ち、CRuby と同じく全関数は rb_st_* で、st_insert などは #define で届く。ruby.h が末尾で ruby/st.h を include する （CRuby と同じく、<ruby/st.h> を自分で include しない拡張のため。 enum st_retval はそちらへ移した）。メモリは ruby_xmalloc 系 （GC 圧力に数える）、テーブルが st_index_t を越えると RuntimeError （オリジナルの RUBY 構成どおり）。

同じコードなので、挿入順の走査、st_hash / st_hash_uint / st_numhash の値、st_memsize まで CRuby と一致する。tests/capi/capi_st.c が numtable（1000 件の挿入・再挿入・delete / shift / foreach の ST_DELETE / ST_STOP、update の 3 経路、insert2、add_direct、 copy / clear、bins の無い小テーブル）、strtable / strcasetable （別ポインタ同内容の検索、st_strcasecmp）、独自 st_hash_type （衝突だらけの hash で foreach_check / foreach_with_replace / keys_check / delete_safe + cleanup_safe）、hash 関数群、 VALUE を鍵と値に持つ TypedData（mark で st_foreach）を CRuby と比べる。 rb_memhash は st_hash(ptr, len, 0)（CRuby はプロセスごとの seed を 混ぜるが、同一プロセス内で等しいことだけが契約）。

ホストの gem cache にある C 拡張で st_table を使うのは nokogiri だけ （monoruby では ext/nokogiri が肩代わり）なので、実 gem での検証は無い。 oj / ruby-prof / stackprof のような st_table を使う gem がこれで ビルドできる。

3.13 ruby/re.h（段階 6）

strscan のように Onigmo を自分で回す拡張のための面。ruby/onigmo.h は monoruby がリンクしている onigmo-regex crate の onigmo/onigmo.h そのもの（Onigmo 6.2）で、OnigRegion / struct re_registers は本物の 構造体なので regs->beg[i] の読み書きは CRuby と同じ。ただし crate の Onigmo は RUBY を定義せずにビルドされていて OnigRegion が history_root を持つ（32 バイト、CRuby は 24）ため、ヘッダの先頭で USE_CAPTURE_HISTORY を強制し、拡張がスタックに置く構造体をライブラリと そろえる（そろえないと onig_region_init がスタックを壊す）。

拡張の .so は monoruby のバイナリのシンボルを解決できないので、 onig_search / onig_match / onig_region_* / onig_free / onig_name_to_backref_number / onig_foreach_name / onig_number_of_* / onig_error_code_to_str は capi.c の薄い関数で、 MrApi::onig_api() が返す MrOnigApi テーブル（void * で型を消した 関数ポインタ）経由で monoruby 内の Onigmo を呼ぶ。onig_new と エンコーディング / 構文のテーブル（データシンボル）は出さない。 パターンは Regexp を作って得る（rb_reg_regcomp）。

regex_t は monoruby のもの。rb_reg_prepare_re(re, str) は Regexp#match が str を相手に使う codec（RegexpInner::capi_compile_key: check_match_encoding で互換性を検査し、ネイティブ codec なら素のパターン バイト列とその encoding、さもなくば engine が持つ変換済みパターン）で onig_new したバッファを (pattern, option, encoding) 鍵のキャッシュから 返す（ext::capi_regex、プロセスの寿命まで解放しない）。RREGEXP_PTR(re) （rb_reg_ptr）は Regexp 自身の codec のもので、onig_foreach_name などの パターン側の問い合わせ用。CRuby の struct RRegexp は無いので RREGEXP(re)->ptr は書けず、RREGEXP_PTR / RREGEXP_SRC は呼び出し。 どちらの regex_t も onig_free してはいけない。

rb_reg_onig_match(re, str, match_fn, args, regs) は CRuby 3.3 の形 （ONIG_MISMATCH を返す、ONIGERR_TIMEOUT は Regexp::TimeoutError、 ほかの負値は RegexpError）、rb_reg_region_copy は onig_region_copy に失敗時の rb_memerror、onig_region_memsize は CRuby の計算。 rb_memsearch はバイト検索（enc は使わない。ASCII 互換 encoding では CRuby も同じ）。rb_long2int、rb_deprecate_constant、_((args)) / __((args))（ruby/backward/2/stdarg.h の K&R 移行マクロ、strscan が まだ使う）も足した。

rb_enc_precise_mbclen は monoruby 自身の走査（value::precise_mbclen: UTF-8、EUC-JP / Shift_JIS 系、UTF-16 / 32、それ以外は 1 バイト）を MrApi::enc_precise_mbclen で呼び、答えは CRuby と同じ Onigmo の符号化 （見つかれば長さ、-1 が不正、-1-n が n バイト不足）。ruby/encoding.h の MBCLEN_* は CRuby どおり ONIGENC_MBCLEN_* の別名で、後者は onigmo.h とトークン単位で同じ定義を #ifndef で持つ（両方をどの順で include してもよい）。rb_enc_mbclen / rb_enc_strlen / rb_enc_codepoint_len はその上に乗る（strscan の charpos が EUC-JP で合うのはこれ）。

require の解決も二つ変えた。(1) stand-in（stub/strscan.rb）が当たり、 $LOAD_PATH 上に monoruby でビルドした .so があるとき、同じディレクトリ に gem 自身の .rb（strscan の lib/strscan.rb: require "strscan.so" の後に Ruby 側のメソッドを足す）があればそちらを返す。(2) .so / .bundle 候補の $LOAD_PATH 走査で、monoruby が読めないもの（プローブ 結果に入るホスト CRuby の x86_64-linux/strscan.so）は飛ばして先を見る。 読めるものが無ければ最初のそれを返して従来の LoadError を出す。

検証: tests/capi/capi_re.c（tests/capi.rs の 4 本目）が onig_search / onig_match（UTF-8 / バイナリ / Shift_JIS / EUC-JP の対象、 Encoding::CompatibilityError、不正バイト列の ArgumentError）、 名前付き捕獲、rb_reg_region_copy、rb_memsearch、rb_reg_regcomp / rb_reg_quote / rb_reg_options / rb_reg_nth_match、rb_long2int の RangeError、rb_enc_precise_mbclen の MBCLEN_* 判定を CRuby と比較。 bin/test-gems の strscan（3.1.8、CI は gem install strscan）が StringScanner のほぼ全メソッド（scan_integer の Ruby 側含む）を CRuby と比較する。残る差は $LOADED_FEATURES の順（monoruby は読む前に、 CRuby は読んだ後に登録する）だけ。

3.14 Time API、rb_keyword_given_p、UTF-8 以外の rb_enc_codepoint_len（段階 7）

3.15 拡張内の VALUE を CRuby のビット列に（段階 8）

段階 7 までは VALUE が monoruby の Value そのものだった。Qfalse が 0 でないので、if (fb->io) のように C の真偽で VALUE を見る json 2.18 の 拡張（fbuffer.h、generator.c の if (!data->vstate)）が動かず、 RTEST を使っていない拡張は同じ目に遭う。そこで拡張の中では CRuby の ビット列を使い（§2 の表）、層が境界で変換することにした。

変換は 2 関数 M(VALUE) -> MrValue と R(MrValue) -> VALUE （capi.c 冒頭）。nil / true / false / undef は表引き、Symbol は シフト幅の付け替え、それ以外は恒等。Fixnum と flonum（回転も同じ）と ヒープポインタは両者でビットが同じなので、変換は分岐 4 つと & 0xff だけで済む。どちら側のヒープポインタも相手側の Symbol に見えることは ない（下位バイト 0x0c は 8 の倍数でない）。

境界（どれも capi.c の中で閉じていて、ABI は変わらない）:

  • api-> 呼び出し全部: 引数は M()、戻りは check() / R()。 argv 配列は mr_args() で変換したものを渡す（16 個までスタック、 それ以上は呼び出し単位のバッファ）。
  • Ruby → C の入口 capi_dispatch / block_dispatch: self と argv を R() し、結果を M() して返す。
  • rb_gc_register_address / rb_global_variable: C グローバルには CRuby の値が入っているのでコアには読ませない。層が番地リストを持ち、 pin した隠しネイティブオブジェクト 1 個の mark から変換して報告する （json は rb_global_variable を 5 箇所で使う）。
  • RARRAY_CONST_PTR / RARRAY_PTR: 要素を変換したコピーを返す。 コピーは現在の Ruby 呼び出し（capi_frame の owner）が持ち、呼び出し が戻るとき解放する。1 呼び出しにつき 8 スロット（Array ごとに 1 つ、 同じ Array はスロットを再利用して要素を取り直す）なので、CRuby と同じ ように複数の Array のポインタを同時に持てる。RARRAY_AREF は rb_ary_entry（変換あり）。
  • TypedData の dmark / ブロックの mark: rb_gc_mark(VALUE) が M() してコアに渡す。
  • rb_protect の rb_errinfo、rb_hash_foreach のコールバック、 rb_iter_break の値、など VALUE を保持する層内の構造体はすべて CRuby 側の値で持ち、コアに渡す瞬間だけ変換する。

ヘッダ（ruby/ruby.h）は CRuby の定義そのもの: RTEST(v) は (v & ~Qnil) != 0、IMMEDIATE_P は v & 7、SPECIAL_CONST_P は IMMEDIATE_P || !RTEST、ID2SYM / SYM2ID は 8 ビットシフト。

CRuby と違う点で残るのは「C に渡したポインタ先の要素が生のオブジェクト メモリではない」ことだけ: RARRAY_CONST_PTR に書き込んでも Array は 変わらない（RARRAY_PTR は前から読み取り専用）。

検証: tests/capi/capi_value.c（tests/capi.rs の 6 本目）が定数の 数値、RTEST 等のビット判定、Symbol の往復、flonum / heap float、 rb_global_variable した C グローバル（nil / false / String を入れて GC.start）、RARRAY_CONST_PTR を 2 本同時、rb_ary_new_from_values、 Qundef を返す API、rb_scan_args の省略引数、rb_yield / rb_block_call / rb_protect / rb_ensure / rb_hash_foreach / rb_funcall を通る nil / false、dmark で mark される VALUE を CRuby と比較する。 bin/test-gems に json 2.18.0 が加わり、gem の parser.so / generator.so（stand-in gem/json/ext/*.rb より .so が勝つ）で JSON.generate / parse / pretty_generate / State / Coder / エラーメッセージが CRuby と一致する。既存の 5 フィクスチャと bcrypt / msgpack / strscan / strptime / yajl-ruby も変わらず一致。

3.16 未実装 API はロードを通し、呼ばれたら NotImplementedError

CRuby の公開 C API（monoruby_capi/src/cruby_api.txt、CRuby 4.0 の include/ruby/** の宣言と libruby の export から採った関数名）のうち層が 定義していないものについて、build.rs が capi_unimplemented(name) を呼ぶ weak なスタブを生成し capi/libmonoruby_capi_stubs.a に入れる。 RbConfig の EXTDLDFLAGS（拡張の .so のリンク行にだけ入る）が -lmonoruby_capi_stubs を足すので、拡張にはスタブもリンクされる。

  • 未実装の rb_* を参照するだけの拡張もロードでき、その関数を呼んだ ときに NotImplementedError（rb_foo() is not implemented in monoruby's C API）になる。以前は dlopen（RTLD_NOW）が未解決シンボルで 失敗し、拡張全体が LoadError だった（ruby/spec の optional/capi では 47 ファイル中 22 ファイルがこれで丸ごと落ちていた）。
  • have_func は従来どおり「無い」と答える。mkmf の conftest は EXTDLDFLAGS を使わず LIBRUBYARG（層のアーカイブだけ）でリンクするので、 拡張の #ifdef HAVE_RB_FOO は層に無いものについてフォールバック側を選び 続ける。
  • スタブを出すのは、ビルドした層のアーカイブに（nm で見て）無いシンボル だけ（st_hash_end のようにヘッダのリネームで別名になるものも正しく除外 される）。スタブは weak でもあるので、層が定義する関数は常に層のものが勝つ。
  • ヘッダに宣言の無い関数は C としては暗黙宣言になる（GCC 14 以降は エラー）。宣言はこれまでどおり実装したときに足す。

3.18 C で裏打ちされたグローバル変数、C++ の ANYARGS、alloc 関数の副作用（段階 10）

gosu 1.4.6（SWIG が生成した C++ ラッパー RubyGosu.cxx + C++ 本体）を monoruby bin/gem install でそのままビルドして動かすために足した面。 dewasm の DOOM（gosu のウィンドウに描く）が動作確認の相手。

  • rb_define_variable / rb_define_readonly_variable / rb_define_virtual_variable / rb_define_hooked_variable（rb_gvar_* の getter / setter / marker を含む）: 新しい ABI 項目 gvar_hook が、コア の gvar テーブルに GvarEntry::Native（data ポインタ付きの C の getter / setter）を置く。層は名前ごとの記録 capi_gvar（ID、var、getter、 setter、marker）を持ち、gvar_get_dispatch / gvar_set_dispatch が capi_dispatch と同じフレームを積んで拡張の関数を CRuby の引数で呼ぶ。 setter が rb_gvar_readonly_setter なら setter 無しで登録し、コアが CRuby と同文の NameError（$x is a read-only variable）を出す。var の 先の値は記録の marker（rb_gvar_var_marker は *var、 rb_gvar_val_marker は (VALUE)var）が、pin した 1 つのネイティブ オブジェクトの mark から辿る。defined?($x) は getter を呼ばずに "global-variable"（CRuby と同じ）。alias / trace_var / rb_gv_get はコアの既存の経路がそのまま効く。
  • getter の例外: gvar の読み出しは VM / JIT に例外経路が無い （get_global_var は素の Value を返す）ので、getter が raise すると 警告を出して nil を読む（§6）。setter の例外は普通に伝播する。
  • ruby/backward/cxxanyargs.hpp: C++ としてコンパイルされるとき ruby.h が末尾で include する。CRuby の同名ヘッダと同じく、 VALUE (*)(...) / void (*)(...) / int (*)(...) にキャストした関数 ポインタを受ける overload（rb_define_virtual_variable / rb_define_hooked_variable（nullptr 版含む）、rb_rescue / rb_rescue2 / rb_ensure、rb_iterate / rb_block_call / rb_catch / rb_catch_obj / rb_proc_new、st_foreach / st_foreach_check / rb_ivar_foreach）を提供する。SWIG は VALUEFUNC(f) 等でこの形に揃えて 渡す。rb_define_method 系はマクロのキャストで足りるので CRuby の template dispatcher は持たない。rb_rescue2 の overload のために rb_vrescue2 を足した。
  • HAVE_RB_DEFINE_ALLOC_FUNC: CRuby の ruby/internal/intern/vm.h が 定義する告知。無いと SWIG は Ruby 1.6 向けの new（特異メソッド + rb_obj_call_init）を生成し、キーワード引数が initialize に届かない （Gosu::Window.new(w, h, fullscreen: ...) が ArgumentError）。
  • alloc 関数が置いた ivar: 遅延 alloc（§3.7）でペイロードを本物の インスタンスへ移すとき、一時オブジェクトの ivar も rb_ivar_foreach で 写す（SWIG の alloc は @__swigtype__ を置き、全メソッドの型検査が それを読む）。さらに capi_dispatch は C メソッドのレシーバがペイロード 無しのネイティブオブジェクトなら先に alloc を走らせる （materialize_payload）ので、C の initialize は CRuby の allocate 直後と同じ状態を見る。
  • rb_obj_instance_eval / rb_obj_instance_exec / rb_mod_module_eval / rb_mod_module_exec: 対応する Ruby メソッドの呼び出し。argc == 0 の eval と exec は走っている C メソッドのブロックを渡す。rb_ivar_foreach も足した（#instance_variables に出るものだけ）。
  • strlcpy / strlcat: CRuby の libruby が glibc 2.38 より前の C ライブラリのために持っているもの。date_strftime.c が呼ぶので、glibc 2.35（Ubuntu 22.04）では require "date" が undefined symbol: strlcpy で落ち、psych 経由で gem install も落ちていた。層が weak で定義し （持つ libc ではそちらが勝つ）、config.h が HAVE_STRLCPY / HAVE_STRLCAT を答える。Apple の libc は fortify のマクロとして持って いて関数宣言が書き換えられてしまうので、そこでは宣言も定義もしない。
  • is_capi_extension は dlopen しない: 従来は RTLD_NOW で試し開きし 「CRuby 用の .so は rb_* が未解決で失敗する」としていたが、ホストの CRuby が --enable-shared なら拡張は libruby.so をリンクしていて普通に 開ける。gosu の .so（C++）は dlclose で降りず、libruby とそれが使う SDL 2.33 がプロセスに残り、stand-in（stub/gosu）が FFI で開いた SDL 2.0.18 と同居して segfault した（bundle exec monoruby では vendor/bundle の CRuby 用 .so が $LOAD_PATH にある）。いまは ext/dynsym.rs が ファイルから ELF の .dynsym / Mach-O の LC_SYMTAB を読んで monoruby_capi_init の有無を答え、読めない形式のときだけ従来の dlopen に 落ちる。

検証: tests/capi/capi_vars.c（tests/capi.rs の 10 本目）が 4 種の定義 関数、alias / trace_var / rb_gv_get、instance_eval 系、alloc 関数の ivar を CRuby と比較する。tests/capi/capi_cxx.cpp は SWIG の形の C++ 拡張 （VALUEFUNC キャスト、rb_define_alloc_func 経由の new とキーワード、 $SWIG_TRACKINGS_COUNT 相当の virtual 変数、readonly 変数）で、C++ コンパイラがあれば双方でビルドして比較する。capi_cruby_build_is_not_opened は libruby をリンクし -z nodelete で降りないようにした CRuby 用 .so を $LOAD_PATH に置き、LoadError の後に /proc/self/maps に libruby が 無いことを見る（以前の実装では残った）。

3.21 strscan を Ruby 実装に戻し、層の入口を速く（段階 13）

段階 11 の後、ruby-bench の StringScanner を回すベンチが大きく遅くなった （#1800 前 → 後: ruby-json 175 → 1535 ms、tinygql 172 → 353、 liquid-compile 26 → 38、graphql 18 → 38）。原因は二つ。

  1. 二乗のエンコーディング検査: strscan は String パターンの照合ごとに rb_enc_check(p->str, pattern) を呼ぶ。層はこれを Encoding.compatible? の funcall で済ませていて、core の encoded_operand が subject 全体をコピーして走査し直していた。トークン ごとに入力全体の長さだけ働くので ruby-json は二乗になる。
  2. 呼び出しごとの固定費: JIT → ネイティブラッパー → ext_method_trampoline → capi_dispatch（_setjmp）→ cfunc で 1 回 約 470 Ir。JIT がインライン化する Ruby のメソッドならほぼ 0 で、 tinygql は 1 回の実行で StringScanner を約 980 万回呼ぶ。

1 は直し（下記）、2 は層では消せないので strscan だけ Ruby 実装に戻した。 stringio / zlib は C 拡張のまま。

  • strscan: stdlib/strscan.rb は #1800 前の実装（照合はバイト位置の suffix に対する String#__strscan_match 1 回、MatchData を作らず $~ にも触れない）。monoruby_capi/ext/strscan/ と stdlib/strscan/strscan.rb は削除し、String#__strscan_match / RegexpInner::strscan_match(_bytes) を戻した。ruby/spec library/stringscanner の 7F+58E は Ruby 側で直した: fixed_anchor: （と fixed_anchor?）、scan_full / search_full、scan_byte / peek_byte、scan_integer(base: 10 | 16)（strscan 3.1.3 以降の 0x の扱い）、named_captures（失敗した照合のパターンも覚える）、 must_C_version、StringValue（to_str）での initialize / string= / concat、負の pos=、負の peek の ArgumentError、 CRuby と同じ inspect（前後 5 バイトをバイナリとして dump）。 fixed_anchor: true のスキャナだけが特異モジュールから全体照合版の マッチャを受け取るので、ふつうのスキャナは照合ごとのフラグ判定も 7 つ目の ivar（inline 枠は 6）も持たない。initialize(str, options = nil) は CRuby の rb_scan_args("11") の形で、fixed_anchor: は Hash の位置 引数として届く（キーワードを受けるより安い）。
  • 層の高速化（stringio / zlib と、ほかの C 拡張にも効く）:
    • rb_enc_compatible / rb_enc_check は両方が String なら C で enc_compatible_latter を辿る。コードレンジは String のキャッシュを 読む。core の EncodedOperand も String をコピーせずに持ち、キャッシュ 済みのコードレンジを使う（Encoding.compatible? 自体も速くなった）。
    • RSTRING_PTR / RSTRING_LEN はヘッダの static inline で String セルを 直接読む（inline / heap / 共有の 3 形、それ以外は関数に落ちる）。 レイアウトは string.rs の const assert で固定。rb_enc_get は String のエンコーディングタグ（+ ペイロード）をキーにした 64 要素の 表を引く。
    • rb_reg_prepare_re: 7 ビットの subject には core の engine_for / CRuby の rb_reg_prepare_enc と同じく US-ASCII のエンジンを渡す （RegexpInner::ascii_eligible）。
    • ext.rs: メソッド表を Vec<Option<ExtMethod>> に、トランポリンは 引数を 16 要素のスタック配列にコピーし、可変長引数のメソッドは 固定 8 スロット + あふれた分の Array（set_native_variadic）で受ける （引数ごとの Array 確保をやめた）。
  • 結果（release、ruby-bench の反復の中央値）: #1800 前 → この段階で ruby-json 172 → 170 ms、tinygql 172 → 172、liquid-compile 25 → 26、 graphql 18 → 18。liquid-compile の残り（+0.7% Ir）は initialize の省略可能引数で StringScanner.new が JIT の inline 構築（frameless の initialize）から外れる分。C 拡張のままの層の 効果は段階 11 比で StringIO#write のループ −13% Ir、gets −8%。 ruby/spec library/stringscanner 240 / stringio 703 / zlib 148 例 すべて通過。

3.22 socket も CRuby の C 拡張に（段階 14）

src/builtins/socket.rs（2,900 行のネイティブ実装）と stdlib/socket.rb の 上乗せは、ruby/spec の library/socket で 1169 例中 139F+557E 落ちていた （CRuby は 1463 例）。CRuby 4.0.9 の ext/socket をそのまま層でビルドし、 stdlib/socket.rb は CRuby の ext/socket/lib/socket.rb（require 'socket.so'） にした。

  • ソース: monoruby_capi/ext/socket/（.c / .h、生成済みの constdefs.c / constdefs.h）。CRuby の内部ヘッダ（internal.h、 internal/*.h）は使う数関数だけを宣言する代役を同じ場所に置いた。 extconf.h は extconf.rb の検査結果: Linux（glibc、x86-64 / aarch64）は 実行した記録、macOS は同じ検査からの導出（BSD の sa_len 類、 getpeereid、struct tcp_info なし）。Linux は _GNU_SOURCE、macOS は __APPLE_USE_RFC_3542 を足す（Ext の linux / macos 欄）。
  • rb_io_t: monoruby の IO に struct rb_io は無い。GetOpenFile / MakeOpenFile / RFILE(io)->fptr は層が持つ struct rb_io を、それを求めた Ruby 呼び出し（owner フレーム）の間だけ渡す。中身は ABI io_state で オブジェクトから埋め（fd、FMODE ビット、読み込み済みバッファ）、 io_update で書き戻す: 新しいオブジェクトの fd に入れた記述子はその IO が 引き取り、close_read が落とした FMODE_READABLE はその向きを閉じ、 インタプリタが使わない FMODE ビット（FMODE_NOREVLOOKUP、FMODE_UNIX …）は IoInner の欄に残り、消費した rbuf は捨てる。書き戻しは Ruby を呼ぶ前 （funcall の入口）とフレームの終わり、呼んだ後は読み直すので、Ruby 側の close は CRuby と同じく fd == -1 に見える。
  • 待ち: rb_io_wait はファイバースケジューラがあればその io_wait の答えを そのまま、無ければ IO#wait（IO#timeout を既定に。IO#timeout / timeout= は今回足した。インタプリタ自身の read / write は見ない）、 時間切れは false。rb_io_maybe_wait*、rb_wait_for_single_fd、 rb_thread_fd_select（rb_fdset_t）は GVL を外した poll / select。 rb_io_blocking_region は記述子が非ブロッキングなら GVL を持ったまま呼ぶ （拡張のソケットは全部 SOCK_NONBLOCK で、EAGAIN は rb_io_wait へ行くので すぐ返る。recv ごとの GVL の手放しと取り直しが無くなり、関数内の RSTRING_PTR も安全）。ブロッキングなら GVL を外す。
  • 他に層に足したもの: rb_thread_check_ints（GVL を一度手放して保留の 割り込みを受ける）、rb_thread_prevent_fork、rb_thread_register_exiting （CRuby 4.0.9 の raddrinfo.c は getaddrinfo を joinable な pthread で 走らせ、終了時にこれを呼んで VM に fork 前の join を頼む。層の prevent_fork はただの呼び出しで、そのスレッドを追跡しないので空実装）、 rb_readwrite_syserr_fail （IO::EAGAINWaitReadable など）、rb_fiber_scheduler_*、 rb_eIOTimeoutError / rb_mWaitReadable / rb_mWaitWritable、RB_INT2NUM 類、 UIDT2NUM / GIDT2NUM、rb_nogvl での errno の持ち越し（CRuby と同じく 呼び出し側が失敗した syscall の errno を読む）。
  • rb_str_modify がバッファを潰していた: str_cptr は長さの位置に NUL を 書くので、rb_str_modify_expand した容量に recv してから rb_str_modify + rb_str_set_len する形（read_nonblock / recv の出力バッファ）で先頭バイトが 0 になった。ABI str_modify は共有の切り離しとコードレンジの破棄だけをする。
  • IO のサブクラスの new: IO.new はネイティブで initialize を通らずに ストリームを作っていた。initialize を自前で持つサブクラス（ソケットの クラス）は Class#new と同じ allocate + initialize に回す（builtins/io.rb）。
  • 結果: ruby/spec library/socket 1463 例で 1F（IO#close が待っている ファイバーをスケジューラの fiber_interrupt で起こす、コア側の 4.0 の機能）、 library/net-ftp 461 例で 4E（すべて OpenSSL::SSL の定数。§3.23 で 0E）。 両スレッドモデルで同じ。

3.23 openssl も CRuby の C 拡張に（段階 15）

stdlib/openssl.rb は Digest / HMAC / PBKDF2 / KDF を ext/digest の上に、 Cipher の AES-GCM / CBC を ext/openssl（RustCrypto）の上に Ruby で書き、 PKey / X509 / SSL は読み込めるだけの空の殻だった（ruby/spec library/openssl 171 例中 21F+66E、library/net-ftp は OpenSSL::SSL の定数で落ちる）。 CRuby 4.0.9 の ext/openssl をそのまま層でビルドし、システムの OpenSSL （Linux は libssl-dev、macOS は Homebrew の openssl@3）に動的リンクする。 stdlib/openssl.rb と stdlib/openssl/*.rb は CRuby の ext/openssl/lib/ （require 'openssl.so'）。ext/openssl crate は削除した。

  • OpenSSL の見つけ方（build.rs openssl_link）: openssl-sys と同じ順で OPENSSL_DIR（<dir>/include、<dir>/lib）、pkg-config openssl、 Homebrew の keg-only な openssl@3（pkg-config の既定の探索路に無い）、 コンパイラ自身の探索路。openssl/ssl.h が見つからなければ拡張は作らず 警告だけ出す（require "openssl" が LoadError になる。monoruby 自体は動く）。 extconf.h は OpenSSL 3.x に対する extconf.rb の検査結果。
  • 層に足したもの: rb_attr（rb_define_attr と同じく常に public。 C から attr_reader を呼ぶと拡張を require した場所の可視性、トップレベルの private になる）、rb_str_drop_bytes、ruby_verbose / ruby_debug （rb_ruby_verbose_ptr: 呼ぶたびにグローバルから読み直すポインタ）、 rb_thread_call_with_gvl（GVL を外した区間の中からは呼ばない: 鍵生成の 割り込み確認だけが使い、区間が返ってから届く）、RHASH_SET_IFNONE、 ruby/assert.h（RUBY_DEBUG なしの CRuby と同じく検査しない）。
  • rb_obj_class: rb_class_of を返していたので、クラスオブジェクトには そのメタクラスが返り、StringValue(klass) の TypeError が #<Class:OpenSSL::Digest::SHA1> になった。ABI obj_class で特異クラスを 飛ばした本当のクラスを返す。
  • Digest::Class（monoruby の Ruby 実装 stdlib/digest.rb）: CRuby の digest.c と同じく hexdigest(*args) は digest(*args) を通る （OpenSSL::Digest.digest(name, data) が引数の順を入れ替えて再定義する）。 引数なしの Instance#digest は複製の finish（OpenSSL::Digest の finish は読んだ状態を消費する）。
  • 結果: ruby/spec library/openssl 173 例 / library/net-ftp 461 例とも 0F 0E。

3.24 ホストの CRuby が入れた gem の C 拡張を monoruby 向けに建て直す（段階 16）

ruby-bench のハーネスはホストの CRuby で bundle install し、monoruby は そのバンドルを Bundler.setup で使う。gem の .so は CRuby のヘッダで ビルドされているので読めない（§2）。graphql-native（graphql-c_parser）と liquid-c はこれで止まっていた。

  • 再ビルド: require が CRuby 向けの .so に当たると （RequireLoad::Foreign、判別はこれまでどおりシンボル表）、 Executor::build_host_extension が stdlib/monoruby_hooks/host_extension.rb の Gem::MonorubyHostExtension.build を呼ぶ。.so を含む gem を Gem.loaded_specs から（なければ全 spec から）探し、拡張がすべて extconf.rb のときだけ、gem のツリーを一時ディレクトリに写して （ホストのツリーは読むだけ）ホストのビルド残り（*.o / *.so）を消し、 Gem::Ext::ExtConfBuilder で層に対してビルドする。置き場所は monoruby の gem home の host_extensions/<platform>/<gem>-<version>/（gem の extension_dir と同じ並び）で、$LOAD_PATH の先頭に足すので、同じ gem の ほかの拡張ファイルはそのまま見つかる。gem.build_complete に gem のパスと libmonoruby_capi.a の大きさ・mtime を書き、層が変われば建て直す。 並行実行は flock で 1 回に絞る。失敗はログ（<gem>.gem_make.out）を残して 1 度だけ警告し、元の LoadError を返す。extconf と make は Bundler.with_unbundled_env の中で走る（子の monoruby が -rbundler/setup でベンチのバンドルを立ち上げないように）。 bin/test-gems の「the host-installed extension is rebuilt for monoruby」（もと tests/mkmf.rs の host_installed_gem_extension_is_rebuilt）。
  • alloc 関数が self を覚える（liquid-c の body->self）: 遅延 alloc （§3.7）は一時オブジェクトに alloc 関数を走らせて記録を本物に移すので、 記録の中に保存された self が一時オブジェクトを指していた。alloc 関数の 実行中は「いま埋めている本物」（pending_alloc）を覚え、同じクラスの Data_Wrap_Struct / TypedData_Wrap_Struct はその本物を返す。
  • rb_str_capacity: 空の String や共有バッファの String に 0 を返して いたので、「容量が足りなければ倍にする」ループ（liquid-c の c_buffer）が止まらなかった。CRuby の埋め込み容量 23 を下限に、共有なら 長さを答える（RStringInner::c_capacity）。
  • ruby_vsnprintf の無限ループ: SUBST_PUT(ch) がバッファに空きがある ときしか引数を評価せず、digits[--nd] の副作用が飛んで %lld の桁が 尽きなかった（snprintf(NULL, 0, ...) で必ず起きる）。引数は 1 度だけ 評価する。
  • 足した API: rb_check_symbol / rb_check_symbol_cstr / rb_check_id_cstr（ABI intern_check: 既に intern されていれば返し、 なければ intern しない）、rb_obj_encoding、rb_str_dup_frozen、 rb_utf8_str_new_literal、RB_NUM2LL 系マクロ、<alloca.h>、 ruby/vm.h の ruby_vm_at_exit（プロセス終了時に逆順で呼ぶ）。 tests/capi/capi_gaps.c。

15CRuby の ext/openssl を層でビルドしシステムの OpenSSL にリンク（ext/openssl crate と Ruby 実装を削除）、rb_attr、ruby_verbose、rb_obj_class の ABI済（§3.23、ruby/spec library/openssl / net-ftp 全通過）
16ホストの CRuby が入れた gem の C 拡張を層で建て直して読む、alloc 関数の self、rb_str_capacity の下限、ruby_vsnprintf の無限ループ、rb_check_symbol 系済（§3.24、ruby-bench の graphql-native / liquid-c が完走、liquid-c の出力は CRuby と一致）

6. 既知の制約

  • rb_scan_args の : は「末尾の引数が Hash ならキーワード」とみなす （f({a: 1}) と f(a: 1) を区別しない。rb_keyword_given_p は区別する、 §3.14）。
  • rb_protect で捕まえた大域脱出（§5）は、rb_errinfo で取り出すと クラス Exception のオブジェクトに見える（rb_jump_tag で再送すれば 元の脱出に戻る）。
  • GC 中に走る dfree / mark 関数から C API の関数を呼ぶと止まる （markly の RTYPEDDATA_DATA(self) = NULL、sqlite3 の aggregate の finalize）。rb_gc_mark 系だけが使える。
  • rb_iter_break は隠し例外で実装しているので、rb_block_call / rb_iterate の外（rb_funcall で呼んだメソッドに渡した rb_proc_new の Proc の中など）で使うとその例外が外へ出る。
  • rb_proc_new の Proc は Method#to_proc 由来なので lambda? が true （CRuby は false）。arity は同じ -1。
  • alloc 関数は遅延して呼ばれる（§3.7）。ペイロードが読まれるか、その インスタンスで C のメソッドが走るまでは alloc 関数はまだ走っておらず、 alloc 関数が置く ivar も無い（§3.18）。写すのは #instance_variables に 出る ivar だけで、隠し ivar は写らない。
  • C で裏打ちされたグローバル変数の getter が raise しても、読み出しは 警告を出して nil になる（VM / JIT の gvar 読み出しに例外経路が無い）。 setter の例外は伝播する。
  • cxxanyargs.hpp は rb_define_method 系の template dispatcher と、 rb_hash_foreach / rb_fiber_new / rb_thread_create の overload を 持たない（前二者はマクロが受ける、後二者は層に無い）。
  • dsize / dcompact は使わない。RUBY_TYPED_* のフラグはすべて無視。
  • rb_warn は Kernel#warn("warning: ...")（ファイル名・行番号は付かない）。
  • rb_gv_get / rb_gv_set は eval 経由。
  • mkmf の create_header は使えるが、$(hdrdir)/ruby/backward/2/* の中身 は無い。RbConfig::CONFIG["CC"] は Linux では スナップショットの gcc のまま（CC 環境変数で上書きできる）。
  • RARRAY_CONST_PTR / RARRAY_PTR が指すのは要素のコピー（§3.15）。 書き込みは Array に届かず、1 回の Ruby 呼び出しの中で 9 本目の Array の ポインタを取ると最初のものが使い回される。
  • ruby/re.h は onig_new と Onigmo のテーブル群を出さない（§3.13）。 OnigRegion は CRuby より 8 バイト大きい（history_root）。 rb_reg_prepare_re のバッファは解放されない。
  • rb_enc_codepoint_len が符号位置を組み立てるのは UTF-8 だけ（ほかの 多バイト encoding では先頭バイトを返す）。ENC_CODERANGE は呼ぶたびに 計算する。
  • ALLOCV の確保は例外で巻き戻ると解放されない（CRuby は String に 載せて GC に任せる）。
  • ホスト CRuby に同じ gem があると、require "msgpack" の Ruby 側 （lib/msgpack.rb）はプローブ結果にあるホストの lib/ から読まれ、 .so だけ monoruby の gem home のものになる。gem "msgpack" で monoruby 側を先に activate すれば両方そろう。
  • gem install は monoruby の gem home に入れる。ホスト CRuby で 入れた C 拡張 gem の .so は monoruby では読めない（stub のあるものは stub が読まれる）ので、monoruby で使うには monoruby で入れ直す。
