## 0. 採った解釈と、先に読むべき結論

### 0.1 解釈

- 「不動点探索の改善」は、ループヘッドの後退辺不動点
  (`compile/loop_analysis.rs`)の **停止性・検査可能性・コスト** の改善と解釈した。
  型と配置の分離は `regalloc_separation.md` §13.8 / §16.6 / §31.2 の否定的結果に従い、
  今回の計画の対象外とする(§5.1)。
- 依頼文のたたき台(ゴール 4 件・手順 6 件)は検証のうえ **組み替えた**。
  対応は §3 と §4 の各項に書いた。
- 計測は、リポジトリの外に置いた作業コピーに一時的な計測コードを入れて行った
  (差分は §7)。リポジトリ本体は `doc/fixpoint_engine_plan.md` の追加だけである。
- 作業中にユーザーから「meet は単調で束に上界があるので必ず停止するはず」という
  指摘を受けた。§2.2〜2.4 がその検証で、計画全体をこの結果に合わせて直している。
- 続けて「後退辺を前回との join で記録すると性能が落ちるか」の検証を依頼され、
  §2.7 に結果を書いた。初版の結論 2 と §2.4 の帰結はこの結果で **訂正した**。

### 0.2 結論(4 点)

1. **停止はするが、上限が先に尽きてプロセスが abort する。再現できる。**
   上限 `10 × ヘッド数`(`loop_analysis.rs:54`)は束の鎖の長さと無関係で、
   コピーが連鎖するループでは収束する列が上限に先に当たる。
   12 タップの遅延線を素直に書いたメソッド(§2.3)が
   `panic!("not fixed")`(`loop_analysis.rs:133`)で落ち、x86-64 では
   `extern "C"` 境界を越えるためプロセスごと abort する。上限を外すと
   同じコードは 13 walk で収束し、結果は CRuby と一致する。
2. **後退辺の列は上昇列ではない。** `so_mandelbrot` で、後退辺が walk 0 の
   `S(Value)` から walk 1 の `F`(Float)へ **下がる** 更新を 1 件観測した(§2.4)。
   join は単調だが、内側ループヘッドの float 採用(`keep_backedge_floats`)が
   ヘッドを `incoming ⊔ backedge` より狭くするためである(解析 walk の採用を切ると
   下降は消える。§2.7)。
   **訂正:** 初版は「前回との join で上昇列にする直し方は退行を招くので採れない」と
   書いたが、実測では退行しなかった(§2.7)。join にすると後退辺の列は構成上の
   上昇列になり、ユーザー指摘の停止性の議論がそのまま成り立つ。手順 A′ として加えた。
3. **walk は JIT 時間の 1/4〜1/2 強を占め、その 2〜3 割は省略できる見込みがある。**
   `app_aobench` で walk 137 回のうち 39 回、optcarrot で 153 回のうち 35 回は、
   入口状態が直前の walk と完全に一致していた(§2.5)。決定的な抽象実行なら
   結果も同じなので、確認のためだけの walk である。
4. **インライン生成器への型シグネチャ別登録は見送る**(§5.2)。生成器は
   すでに解析・生成の両モードで同じ遷移関数として動いており、別登録は二重管理になる。

推奨する着手順は §6(A → B → E → A′ → D → §5.4 → F)。最初の一手は手順 A
(上限の是正と abort の解消)である。

## 1. 現状の整理

### 1.1 呼び出し構造

| 段 | 場所 | 役割 |
|---|---|---|
| 合流 | `merge.rs:75` `incoming_context` | BB の入口で前任の状態を join。ループヘッドなら下へ |
| 種付け | `merge.rs:587` `analyse_loop_head` | 要素読みされるローカルを `Array` と仮定して不動点を回し、外れたらやり直す |
| 反復 | `loop_analysis.rs:38` `analyse_backedge_fixpoint` | 収束まで walk を繰り返す。上限 `10 × heads.len()`(:54)、超過で `panic!`(:133) |
| 1 walk | `loop_analysis.rs:139` `analyse_loop` | 使い捨ての `JitContext` でループ範囲の BB を順に歩く |
| 1 BB | `loop_analysis.rs:239` `analyse_basic_block` | 本番と同じ `compile_instruction` を実行(:255) |
| 文脈 | `context.rs:1353` `loop_analysis` / `:1371` `analysis_clone` | `codegen_mode: false`。`spec_memo` だけ共有 |

- 1 回の walk が入れ子全体を覆う。内側ヘッドは自前の不動点を回さず、前回の walk が
  記録した後退辺と合流する(`loop_analysis.rs:20-37` のコメント、
  `incoming_context(bbid, true)`)。
- walk 自身のヘッドには `loop_info` を渡さない(`context.rs:1357-1362`)。
  記録済み後退辺は `analyse_loop` が入口状態へ join する(`loop_analysis.rs:153-161`)。
- 解析モードでは `AsmIr::push` が抑止され命令列は作られない
  (`regalloc_separation.md` §10、§11)。

### 1.2 反復の形と収束判定

1 回の walk を関数 F とすると、反復は次の形である。

```
head_n   = incoming ⊔ be_{n-1}          (analyse_loop: state.join(backedge))
be_n     = F(head_n)                    (ループ範囲を 1 回歩いた後退辺の join)
記録     : be_n が be_{n-1} と equiv でなければ be_n で **置き換える**(loop_analysis.rs:100)
終了     : どのヘッドも変化しなければ終了(:129)
```

- **前回との join は取らず、置き換えである。** 列が上昇するかどうかは F の性質に依る。
- 収束判定 `equiv` は全フレームを見る(`state.rs:474`)。フレームごとに
  「スロットの型が一致」かつ「`Invariants` が完全一致」(`state.rs:759`)。
  スロットは `LinkMode::equiv`(`slot.rs:2604`)で、`S`/`F`/`Sf` は `guarded()` の
  一致だけを見て配置を無視し、`C(v)` は値の一致、番兵(`None`/`MaybeNone`/`V`)は
  完全一致を要求する。
- `equiv` が見ないもの: fpr の配置、liveness(`IsUsed`)、省略オブジェクト
  (`virtuals`)、float 読みの印、ループ採用の veto。liveness と veto は毎 walk
  上書きされる(`loop_analysis.rs:80`、`:125`)。
- 後退辺が今回の walk で消えた場合は記録済みのものを残す(`loop_analysis.rs:104-127`)。
  コメントは「後の walk の入口状態が後退辺の分岐を静的に刈ることがある」と理由を書いている。
  これは F が単調でなかった実例の記録である。

### 1.3 束

- 型は `Guarded`(`slot.rs:2789`): `Value`(⊤)、`Fixnum`、`Float`、`Class(c)`、
  `NilOr(NonNil)`。上限は `join_raw`(`slot.rs:2929`): 等しければそのまま、
  nil と非 nil 型は `NilOr` に畳み、それ以外は `Value`。
  束の法則は `guarded_join_lattice_laws`(`slot.rs:3591`)が検査している。
- スロットの状態 `LinkMode`(`slot.rs:2530`)まで含めた鎖は
  `C(v)` → 基本型 → `NilOr` → `Value` で、**1 スロットあたり高々 3 段**。
  `Sf` の `SfGuarded` は `Fixnum`/`Float` → `FixnumOrFloat`(型としては `Value`)。
- `Invariants` は 6 個の真偽値で、join は AND(`state.rs:1590`)。
- 合流は `decide_join`(`join.rs:288`、純粋)と `apply_join`(`join.rs:376`、
  fpr 割り付けを伴う)に分かれ、型の結果が `join_ty` と一致することを
  debug で毎回検査している(`join.rs:178` `verify_join_replay`)。

## 2. 検証と実測

### 2.1 方法

- `cargo build --release`(x86-64 Linux、2 vCPU のクラウドコンテナ)。
- 既存の `jit-debug`(`analyse iteration[x]` の出力)と `jit-log`
  (`jit_stats` の memo ヒット数、`elapsed JIT compile time`)に加え、
  作業コピーへ計測用カウンタを入れた版を使った(§7)。
- **できなかったこと。** このコンテナの `ruby` は 3.3.6 で、ピン留めの 4.0.9 ではない。
  テストスイートは走らせていない。数値は各 1 回の実行で、時間は目安である。
  aarch64 は未確認。

### 2.2 ユーザー指摘の検証 —— join は単調、しかし列は F 次第

指摘のうち join 側は正しい。`join_raw` は有限高の束の上限で、`Invariants` の
join も単調、`equiv` は配置を見ない。問題は残り 2 点にある。

1. 後退辺は置き換えなので、上昇列になるには **F(body 全体の抽象実行)の単調性**が要る。
   これはどこにも保証されていない。
2. 列が上昇列で停止が保証されていても、**上限 `10 × ヘッド数` は鎖の長さ
   (およそ スロット数 × 3 段 × フレーム数)と無関係**である。

### 2.3 実測 1: 上限が先に尽きる(プロセス abort の再現)

コピーの連鎖 `a0 = a1; a1 = a2; …` は、型の変化が walk 1 回につき 1 スロット分しか
伝わらない。メソッド JIT では入口が定数(`C(0)`)なので、連鎖の長さ + 1 回の walk が要る。

```ruby
def fir(n)                       # 12 タップの遅延線
  d0 = d1 = d2 = d3 = d4 = d5 = d6 = d7 = d8 = d9 = d10 = d11 = 0.0
  acc = 0.0
  i = 0
  while i < n
    d0, d1, d2, d3, d4, d5, d6, d7, d8, d9, d10 = d1, d2, d3, d4, d5, d6, d7, d8, d9, d10, d11
    d11 = i * 0.5
    acc += (d0 + d1 + d2 + d3 + d4 + d5 + d6 + d7 + d8 + d9 + d10 + d11) / 12.0
    i += 1
  end
  acc
end
40.times { fir(100) }
```

| スクリプト | 既定のビルド | 上限を外した場合 | CRuby 3.3.6 |
|---|---|---|---|
| ローカル 9 個の連鎖(Integer → Float) | 正常終了 | — | 一致 |
| ローカル 10 個の連鎖 | **abort**(`not fixed`) | 11 walk で収束、`46.5` | `46.5` |
| ローカル 24 個の連鎖 | **abort** | 25 walk で収束、`25.5` | `25.5` |
| 上の `fir` | **abort** | 13 walk で収束、`2211.9166…` | 一致 |
| 入れ子 2 段 + 21 個の連鎖 | **abort** | 23 walk で収束、`90.0` | `90.0` |

- `--no-jit` では正しく動く。abort は `jit_profile_patch` 経由のコンパイルで
  panic が `extern "C"` 境界へ達するためである(`compiler.rs:1015` の
  `jit_profile_patch` に `catch_unwind` は無く、`:986-1000` の `jit_compile_patch` では
  コメントアウトされている)。
- 定数初期化が効くのはメソッド JIT と特殊化された呼び出し先である。
  ループ JIT は入口が全スロット `S(Value)` なので連鎖が起きない
  (`regalloc_separation.md` §15.5 と同じ事情)。
- `0.0` 初期化でも起きる。`C(0.0)` と `F` は型が同じ Float でも `equiv` では
  別物(`slot.rs:2604`)なので、やはり 1 walk に 1 スロットずつ動く。

### 2.4 実測 2: 後退辺が下がる更新がある

「記録済みの後退辺 old と新しい後退辺 new について `old ⊔ new` が new と equiv」
を検査した。成り立たなければ上昇ではない。

| ベンチマーク | 検査できた更新 | 上昇でない更新 |
|---|---|---|
| so_mandelbrot | 6 | **1** |
| so_nbody | 3 | 0 |
| app_aobench | 43 | 0 |
| optcarrot | 28 | 0 |
| bf / quick_sort / binarytrees | 4 / 3 / 1 | 0 |

`so_mandelbrot` の 1 件は、外側ループ(BB1)の後退辺で `%7`〜`%10`、`%13`、`%14` が
walk 0 の `S(Value)` から walk 1 の `F(FPReg0..5)` に変わるものだった。型は
`Value` → `Float` で、**精密になる方向**である。

原因の見立て(コード読解による推定。walk を 1 命令ずつ追っての確認はしていない):
walk 0 では内側ヘッドに記録済み後退辺が無いので、内側ループの出口は入口のままの
`S(Value)` で抜ける。walk 1 では内側ヘッドに `loop_info` があるので、
`incoming_context` が `keep_backedge_floats`(`merge.rs:323`、`slot.rs:962`)で
float を採用し、出口が `F` になる。この採用は入口ガード付きの
**狭め(narrowing)** で、ヘッドは `incoming ⊔ backedge` より狭くなる。
同じ性質の操作に、ガードの巻き上げ(`merge.rs:199-204`、解析 walk では無効)と
Array の種付け(`merge.rs:587-616`)がある。

帰結:

- 列は「上昇 + 採用による下降」の混合で、単純な Kleene 反復ではない。
  今回の範囲ではすべて 3 walk 以内に収束した。
- join で蓄積すると `Value ⊔ Float = Value` なので、この外側後退辺の `F` は失われる。
  初版はこれを §13.8 / §40 と同種の退行になると予想したが、**実測では退行しなかった**
  (§2.7)。失われる `F` は外側ループでは使われない値だった。

読み方と注意:

- 「walk 時間」は最外の walk だけの合計で、入れ子の二重計上は除いてある。
  起動時のコンパイル分(app_fib の行、約 0.18 ms)を含む。「JIT 時間」は
  `elapsed JIT compile time` で、起動時の分を含まない。したがって比は目安で、
  小さいベンチほど walk 側が過大に出る。
- それでも aobench で 5 割強、optcarrot で 2 割強が walk である。
- 「入口が直前と一致」は、walk の入口状態が直前の walk と `==`(`AbstractState` の
  導出 `PartialEq`)で、直前の walk で内側ヘッドの記録も外側フレームの widen も
  動いていない回数。この walk は結果が直前と同じになるはずで、
  3 walk で収束する不動点の 3 回目がほぼこれに当たる(aobench 43 件中 39 件)。
  後退辺は変わったが、その差が `incoming` との join で吸収された場合である。
- 上限 10 に近づいた例は通常のベンチには無い。§2.3 の連鎖だけが上限に届く。
- `spec_memo` はループを持つ呼び出し先だけが対象(`method_call.rs:2917`)で、
  1 サイト 8 塔まで(`spec_memo.rs:51`)。ヒットは aobench で 37 回中 11 回、
  optcarrot で 18 回中 8 回。

### 2.6 ZJIT との対比(`053f8da` で再確認)

| | ZJIT | monoruby |
|---|---|---|
| 対象 | SSA の HIR、関数全体 | バイトコード、ループ範囲 |
| 反復 | `infer_types`(`hir.rs:3905`)が RPO で全体を走査 | ヘッドごとに `analyse_backedge_fixpoint` |
| 初期値 | 全値 `Empty`、到達可能性も伝播 | 後退辺「未記録」(`None`) |
| 合流 | ブロック引数へ `union`(`hir_type/mod.rs:546`) | `incoming ⊔ backedge`、その後に採用で狭める |
| 終了 | 型が変わらない、または後退辺を通らなかった(`hir.rs:4058`) | 全ヘッドの後退辺が `equiv` |
| 上限 | **無し**(束の有限性だけ) | `10 × ヘッド数`、超過で panic |
| インライン | HIR を継ぎ足して `infer_types` をやり直す。外側ループは既定 10 周(`options.rs:48`、`hir.rs:7713`)、予算 200(`options.rs:43`) | walk の中で呼び出し先を特殊化コンパイル。`spec_memo` で重複を避ける |
| 組み込み | `FnProperties`(`cruby_methods.rs:33`): `return_type` と `inline` 関数 | `InlineGen` 系のクロージャが状態遷移と生成を兼ねる |

### 2.7 実測 4: 後退辺を前回との join で記録した場合

`loop_analysis.rs:100` の置き換えを join に変えた実験版を作業コピーで作り
(環境変数で切り替え。§7)、同じバイナリで比べた。`new.join(old)` と `old.join(new)` の
2 通り(合流は自分側の配置を優先するので、配置が変わり得る)。

**join が後退辺を実際に広げたベンチは 2 本だけだった。**

| ベンチマーク | join で広がった記録 | 内容 |
|---|---|---|
| so_mandelbrot | 2 | 最外 `for y`(BB1)の後退辺で 6 スロットが `F` → `S(Value)` |
| plb2/matmul | 10 | BB3 の後退辺で 1 スロットが `Sf(Float)` → `S(Value)` |
| so_nbody、app_aobench、bf、quick_sort、binarytrees、plb2 の bedcov / nqueen / sudoku、optcarrot | 0 | 記録される後退辺が同じなので、生成コードも同じ |

**実行命令数(valgrind cachegrind、決定的)。**

| | 置き換え(現状) | `new.join(old)` | `old.join(new)` | 採用を全面的に無効 |
|---|---|---|---|---|
| so_mandelbrot(1000²) | 1,782,981,571 | 1,781,564,546(−0.08%) | 1,781,479,871(−0.08%) | 2,517,401,012(**+41%**) |
| plb2/matmul(n=200) | 1,258,597,984 | 1,257,848,058(−0.06%) | 1,257,857,645(−0.06%) | — |

**時間(so_mandelbrot 3000²、15 回を交互に実行、ユーザー時間の最小値)。**
置き換え 1.750 s、`new.join(old)` 1.750 s、`old.join(new)` 1.797 s、
採用を全面的に無効 1.914 s(+9%)。この環境は雑音が大きく、後退辺が変わらない
app_aobench でも最小値が ±7% 動いた。時間で言えるのは「join による差は雑音以下、
採用の無効化は検出できる」までである。出力はどの設定でも一致した。

**読み取り。**

- **mandelbrot は退行しなかった。** 命令数はわずかに減る。失われる 6 個の `F` は
  最外ループの後退辺のもので、該当スロットは内側で毎回定義し直される。
  現状はそれらを最外ヘッドでも採用しており、入口の unbox と後退辺の移動が余分だった
  と読める(`regalloc_separation.md` §16.4 が指摘した過剰な昇格と同じ形)。
  熱い内側ループの後退辺は join でも変わらない。
- **下降の原因は float 採用で確定。** 解析 walk に限って `keep_backedge_floats` を
  切ると、mandelbrot の非上昇は 0 件になった(§2.4 の推定の裏づけ)。
  採用を全面的に切ると +41% なので、採用そのものは必要である。
- **退行する形を作れなかった。** 「内側ループだけが更新し、外側をまたいで生きる
  float」(`x += j * 0.5` を 2 回回す内側ループ)を試したが、join は一度も
  後退辺を広げず、命令数も同じだった。退行する入力が無いとは言えない。
- **限界。** x86-64 のみ。テストスイートは未実行。実験版の join は省略オブジェクトの
  突き合わせ(`analyse_loop` が join の前に行う `materialize_except`)を省いており、
  そのままでは出荷できない。aarch64 と実機の A/B が要る。

## 3. ゴール

たたき台の 4 件を、§2 の結果に合わせて次のように置き換える。

| | ゴール | たたき台との関係 |
|---|---|---|
| **G1** | 収束する列を上限で打ち切らない。打ち切る場合もプロセスは落とさず、そのコンパイルだけを断念する | 案 1「必ず止まり、止まらなくても壊れない」を、原因(上限が鎖の長さと無関係)に合わせて具体化 |
| **G2** | 反復の性質を **観測できる** ようにする。まず「上昇 / 下降 / 比較不能」を数え、成り立つ不変条件が分かってから assert にする | 案 2「単調性を不変条件にする」は §2.4 により成り立たない。検査対象を「決定性」と「下降は採用由来に限る」に変える |
| **G3** | walk の回数と時間を常時計測し、結果が決まっている walk を省く | 案 3 と同じ。削る対象を実測で特定した |
| **G4** | 束を細かくしても G1〜G3 が自動で追従する形にする(上限と検査が束の定義から導かれる) | 案 4 と同じ。widening は導入せず、有限高を型で保つ方針にする |

## 4. 手順

各手順は独立に出荷できる大きさにしてある。検証は既存の流儀
(CRuby 差分のスイート、debug の shadow 検査、`emit-asm` のバイト一致、
ベンチ A/B は `regalloc_separation.md` §13.4 のゲート)に合わせる。

### A. 上限の是正と abort の解消(G1)

- **目的。** §2.3 の abort を無くす。
- **変更箇所。** `loop_analysis.rs:54` と `:132-134`。
  1. 上限を鎖の長さから導く。案: `heads × (K × Σ_フレーム スロット数 + 定数)`、
     `K` は 1 スロットが動ける回数。`K` と定数は束の側に定数として置き(G4)、
     `LinkMode` の 3 段と下降 1 相ぶんを見込んで当面 `K = 4` とする。
  2. 超過時は `panic!` をやめ、`Err(CompileError)` を返す
     (`analyse_backedge_fixpoint` はすでに `JitResult<()>` を返し、
     `incoming_context` は `?` で伝播する)。ルート単位では
     `compiler.rs:390` の経路で JIT コードが無効化され、VM 実行に残る。
     `jit-log` では超過を 1 行出す。
  3. §2.3 の 5 本を回帰テストに加える(`tests/` に 1 ファイル。`integration.rs` に
     `mod` 行が要る)。
- **検証。** 新しいテストが通ること。通常のベンチで walk 数が変わらないこと
  (上限に届かないので `emit-asm` はバイト一致のはず)。
- **リスク。** (a) 上限を広げるとコンパイル時間の最悪値が伸びる。24 個の連鎖で
  25 walk、ループ本体に比例。気になるなら「walk 数 × ループの命令数」に別の予算を
  掛ける。(b) `Err(CompileError)` が入れ子の特殊化コンパイルやディスパッチの腕の中
  (`context.rs:1095-1106`)で返ったときの扱いは **未確認**。腕の中では単位全体の
  断念になると読めるが、ループ JIT(`position` が `Some`)の後始末と合わせて
  実装時に確認する。
- **たたき台との関係。** 案 2 の「動いたスロットだけ `S(Value)` に widen して再 walk」は
  採らない。§2.3 の連鎖では動いたスロットはすでに `Value` に達しており、
  walk 数は減らない。上限超過は「鎖が長い」だけなので、鎖の長さぶん回すのが正しい。
- **既存文書との関係。** `regalloc_separation.md` §14.1 の「≤10 回」は現状と合わない
  (`10 × ヘッド数`)。本手順で式が変わるので、その際に追記する。

#### A の結果(2026-11-13、基点 `e25cbe8`)

- **基点の訂正。** 計画は `5ed383e` で書いたが、適用時の master は `e25cbe8`
  (#1884、#1885、#1887 などを含む)。`loop_analysis.rs` は `5ed383e` から変わっておらず、
  パッチはそのまま当たった。本文の行番号のうち `merge.rs`(`keep_backedge_floats` は
  :325、`analyse_loop_head` は :602)と `context.rs`(`loop_analysis` は :1400、
  `analysis_clone` は :1418)は数行〜数十行ずれている。
- **abort の再現と解消。** §2.3 の 5 本を `e25cbe8` のリリースビルドで実行すると、
  5 本とも `loop_analysis.rs:133` の `not fixed` で abort した(終了状態 134)。
  手順 A を当てたビルドでは 5 本とも CRuby 4.0.9 と同じ値を出す。
  ローカル 9 個の連鎖はどちらでも正常終了する。
- **生成コードは変わらない(構成上)。** 新しい上限は 1 ヘッドあたり
  `4 × スロット数 + 6 × フレーム数 + 1` で、スロットは `self` を含めて 1 以上、
  フレームは 1 以上なので常に 11 以上になり、旧上限の 10 を下回らない。
  旧上限の中で収束していた不動点は同じ walk 列で収束するので、`emit-asm` の
  比較は行っていない。
- **テストスイート。** CRuby 4.0.9 で `cargo test --test integration` を
  手順 A 側と master の両方で実行した。手順 A 側は 1769 本すべて成功
  (`fixpoint_chain` の 6 本を含む)、master は 1763 本すべて成功で、失敗の集合はどちらも空だった。
  前のセッションで出ていた 27 本の失敗は、3.3.6 で走らせたことによる環境差だった。
- **oracle の 6 行。** CRuby 4.0.9 で 6 本を実行し、記録された値と全行一致した。
- **断念したコンパイルは繰り返されない。** 上限を環境変数で 1〜3 に下げた
  一時ビルド(`jit-log` 付き、リポジトリには入れていない)で確かめた。
  - メソッド JIT: 単位ごとに 1 回だけ `abort compile` が出て、以後は再試行されない。
    `compiler.rs` の `Err(_)` の腕が `invalidate_jit_code` で恒久的に断念し、
    x86-64 では入口を `vm_entry` へ戻す。
  - ループ JIT: 外側・内側のループとも 1 回ずつ断念し、以後は再試行されない。
    `jit_compile_loop` が codeptr を書かずに戻ると、VM の `loop_start` が番兵 `1` を
    書き込み、以後は解釈実行を続ける(x86-64 `vm_loop_start`、aarch64
    `a64_op_loop_start` の両方にある)。
  - 再コンパイルのカウンタ(`whole/loop/spec recompiles`)はすべて 0 だった。
- **注意: 特殊化した呼び出し先の断念は、呼び出し元の単位ごと断念になる。**
  ループを持つメソッド `f` を `k.times { s += f(4) }` から呼ぶ形で上限を下げると、
  `f` を特殊化した `block in caller_m`、`caller_m`、`block in <main>` も
  それぞれ断念した。フレーム付きの特殊化(`specialized_iseq`)は `?` で
  `CompileError` をそのまま上へ伝え、巻き戻して通常の呼び出しにするのは
  frameless の経路(`try_frameless_iseq`)と残差の腕(`method_call_with_residual`)
  だけである。これは手順 A 以前からの `CompileError` 一般の性質で、上限が実際に
  尽きるのは束の鎖を登り切っても止まらない異常時だけなので、当面は手を入れない。
  上限超過を「呼び出し先だけ呼び出しに戻す」扱いにするかは、A′ の後に再検討する。

### A′. 後退辺を前回との join で蓄積する(G1、G2。A の代替または追加)

- **目的。** 後退辺の列を構成上の上昇列にする。そうすれば停止は束の有限性だけから
  従い、A の上限は「鎖の長さ」として証明できる値になり、C の「向き」の検査は
  不要になる。
- **変更箇所。** `loop_analysis.rs:85-102`。記録済みの後退辺があるとき
  `new.join(old)` を記録し、それが old と `equiv` なら変化なしとする。
  join の前に `analyse_loop`(:187-199)と同じ省略オブジェクトの突き合わせが要る。
- **検証。** §2.7 の命令数の再現。mandelbrot / nbody / matmul / optcarrot の A/B
  (§13.4 のゲート、両アーキ)。`stress-spill-pool` 込みのスイート。
- **リスク。** (a) 生成コードが変わる(mandelbrot と matmul で確認済み)。
  今回の範囲では命令数は微減だが、退行する入力が無いとは示せていない。
  (b) コピーの連鎖に必要な walk 数は変わらない。A の上限の是正は依然として要る。
  (c) 内側ヘッドの採用は walk の中に残るので、F 自体は単調にならない。
  上昇が保証されるのは「記録される後退辺」だけである。
- **ユーザー提案との関係。** §5.4 の「巻き上げ → 不動点」の分離を行うなら、
  採用が反復の外に出るので A′ は自然に成り立つ。A′ はその手前で取れる小さな一歩。

### C. 決定性の shadow と、向きの不変条件(G2)

- **目的。** 「同じ入口なら同じ結果」を検査可能な性質として固定する。
  これが D の前提になる。あわせて §2.4 の下降が採用由来に限られるかを確かめる。
- **変更箇所。** `analyse_backedge_fixpoint` に debug 限定で
  1. 入口状態が直前の walk と一致し、文脈(内側ヘッドの記録、外側の widen ログ)も
     動いていないなら、今回の後退辺が直前と **完全一致**(`equiv` ではなく `==`)
     することを assert。
  2. B の「向き」を使い、同じスロットが「上がってから下がり、また上がる」ことが
     無いことを、まず記録し、スイートと ruby/spec で 0 件なら assert にする。
- **検証。** debug ビルドでスイート全体。1 が破れたら、抽象実行のどこかに
  walk をまたぐ隠れた状態がある(`frameless_rejected` は walk ごとに初期化されると
  `context.rs:1410-1413` にある。ほかの候補は未調査)。
- **リスク。** 2 は成り立たない可能性がある。その場合は assert にせず、
  A の上限だけで守る。
- **たたき台との関係。** 手順案 3「後退辺が前回以上であることを assert」は
  `so_mandelbrot` で破れるので、この形に変えた。

### D. 入口が一致した walk の省略(G3)

- **目的。** §2.5 の「入口が直前と一致」した walk を実行しない。
  aobench で walk の 28%、optcarrot で 23%。
- **変更箇所。** `analyse_backedge_fixpoint`。walk の前に入口状態
  (`incoming ⊔ 記録済み後退辺`、liveness をリセットしたもの)を作り、

- **検証。** C の 1 が通っていること(省略する walk の結果が直前と同じである証拠)。

### E. `LinkMode` 段の合流と `equiv` の整合テスト(G2、G4)

- **目的。** `Guarded` の法則は `guarded_join_lattice_laws` があるが、
  `LinkMode` と `equiv` の段には無い。束を触る前に固定する。
- **変更箇所。** `state/slot.rs` か `state/join.rs` のテスト。小さな母集合
  (`C(1)`、`C(1.0)`、`C(nil)`、`S` の各 `Guarded`、`F`、`Sf` の 3 種、番兵)の全組で
  1. `join(a, a)` が `a` と `equiv`、
  2. `join(a, b)` と `join(b, a)` が `equiv`(配置は違ってよい)、
  3. `join(a, b)` が `a`、`b` の両方以上(`join(join(a,b), a)` が `join(a,b)` と `equiv`)、
  4. `equiv(a, b)` なら任意の `c` で `join(a, c)` と `join(b, c)` が `equiv`、
  5. `decide_join` が `unreachable!` に落ちる組の一覧
     (例: `(None, S(_))` は既定の腕で `guarded()` を呼ぶ)を明示し、
     実際に到達しないことをコメントで根拠づける。
- **検証。** テストそのもの。
- **リスク。** 4 は成り立たないかもしれない(`C(v)` 同士は値で、`S` 同士は型で
  比べるため)。破れた組は不動点の収束判定の穴の候補なので、見つかること自体が成果。
- **たたき台との関係。** 手順案 4 と同じ。可換性は「`equiv` の意味で」に限定した。

#### E の結果(2026-11-13)

- **入れたもの。** `state/join.rs` の `link_mode_lattice`。母集合は `C(1)`、`C(1.0)`、
  `C(nil)`、`S` の 8 形(`Value`、`Fixnum`、`Float`、`nil`、任意のクラス、`NilOr` 3 種)、
  `F` と `Sf` 3 種を 2 つのレジスタで、番兵 3 種の計 22 個。`self` と 1 スロットだけの
  フレームを `AbstractFrame::for_test`(テスト限定)で作り、最内フレームの合流
  (`join_with(_, true)`)を `AbstractFrame::equiv` で判定する。
- **結果。** 1(冪等)、2(可換)、3(上界)、4(`equiv` が join の合同関係)は、
  合流が腕を持つすべての組・三つ組で成り立った。破れた組は無かった。
- **5(腕の無い組)。** panic するのは、`None` と型を持つスロット
  (定数、`S`、`F`、`Sf`)の組の両順だけで、19 × 2 = 38 組だった。テストはこの集合を
  固定しているので、組が増えても減っても失敗する。`None` は値を渡されなかった
  省略可能引数の印で、引数の束縛はどの経路でも同じなので、合流の両側で `None` と
  型付きが出会うことは無いと見ている(根拠はコード読解による推定。束縛し得る経路は
  `MaybeNone` になり、`MaybeNone` はどの相手とも合流できる)。
- **テストが失敗し得ることの確認。** `C(l) ⊔ C(r)`(`l == r`)を `S(Value)` に変える
  改変を入れると、debug の `verify_join_replay` がその組で panic し、5 のテストが
  失敗した。法則のテストは panic する組を飛ばすので、腕の無い組の集合を固定する
  5 のテストと組で使う。
- **注意。** これは「1 回の合流」の性質で、不動点の列が上昇することは言っていない。
  下降は合流の外(ループヘッドの float 採用、Array 種付けのやり直し)から来る
  (§2.4、B の結果)。

### F. 束の要素を 1 つ足す試行(G4)

- **目的。** Julia 風の細分化に向け、要素追加の影響範囲と手順を実地で測る。
- **前例。** `NilOr` がすでにこの形で入っている: `profile` フィーチャの

  法則テストを更新した。同じ手順を踏む。
- **設計規則(提案)。**
  1. **有限高を型で保つ。** 合併型は要素数に上限を付ける(PMC の 4 way と揃えるのが
     自然)。Julia が widening を要するのは束が無限高だからで、高さを有限に保てば
     要らない。ZJIT の型がビット集合で有限なのと同じ考え方。
  2. **高さを定数として公開する。** A の上限式と E のテストがそれを参照する。
     要素を足した人が上限を直し忘れても、E のテストが鎖の長さを数えて検出する。
  3. `Guarded` は `Eq + Hash` を導出しているので、`equiv` と `spec_memo` の
     比較・ハッシュは自動で追従する。
- **変更箇所の見積もり。** `Guarded` の列挙を尽くす `match` が要対応になる。

- **検証。** `join_profile` の数値、B の walk 数(高さが増えると walk が増え得る)、
  ベンチ A/B。
- **リスク。** 大きい。A〜E が済んでから着手する。
- **既存文書との関係。** `polymorphic_call.md` §5.3(abstract state に union を

### 5.2 インライン生成器に型シグネチャを別登録するか —— 見送り

- 生成器(`InlineGen` / `InlineGenBinary` / `InlineGenUnary`、`globals.rs:186-241`)は
  解析 walk でも本番でも同じクロージャが走り、結果の型は生成器自身が
  `def_C`、`def_reg2acc_fixnum`、`def_reg2acc_class`、`def_rax2acc` などで状態に書く。
  解析モードでは `ir.push` が抑止されるので、生成器は **そのまま型の遷移関数** である。
- 別登録が要るのは型だけの不動点を別に回す場合だが、それは §13.8 / §16.6 で
  採らないと決まっている。
- 別登録すると、生成器が状態に書く型とシグネチャが食い違う余地が生まれる。
  ZJIT の `FnProperties` は HIR 書き換えと型推論が別パスだから必要な仕組みで、
  monoruby の構造には当てはまらない。
- 代わりに F の段階で検討する価値があるもの: `builtins/` には結果を型なしで
  置く `def_rax2acc` の呼び出しが 18 箇所ほどある(grep による概数)。束を細かく
  したとき、ここに結果型を渡す引数を足すのが ZJIT の `return_type` に相当する改善になる。
- 単調性の面では、生成器が「より精密な入力で辞退する」と F が非単調になる。
  静的には防げないので、C の検査で捕まえる。

### 5.3 ZJIT から取り入れる点、取り入れない点

取り入れる:

- **上限を持たず、束の有限性で止める。** A の上限は「鎖の長さ」から導き、
  超過は異常の検出器として扱う。
- **型が変わらなければ終了、という条件の単純さ。** D は後退辺ではなく入口状態で
  判定することで、これに近づける。
- **有限な型表現**(ビット集合)。F の設計規則 1。

取り入れない:

- **SSA の HIR への全面移行と関数全体の再推論。** monoruby は配置を不動点の中で
  決めることが性能上の前提で(§13.8)、インラインのたびに全体をやり直す方式は
  `spec_memo` が解いている問題を再び作る。
- **`FnProperties` 相当の別登録**(§5.2)。
- **クラス階層に沿った union**(`hir_type/mod.rs:556-` は継承関係から上界を選ぶ)。
  `Guarded` は平坦 + `NilOr` で高さ 3 に収まっており、階層を入れると高さが
  クラスの深さに依存する。

### 5.4 巻き上げと不動点を別パスにする案(ユーザー提案)

提案: ループ内で常に float として読まれるスロットを入口前のガードへ巻き上げる
最適化と不動点探索を一度にやらず、IR を挟んで「巻き上げ → 不動点」に分ける。

**現状は逆順で、しかも循環している。** 採用の判定(`merge.rs:261-264`)は
「後退辺の型が Float かつ loop 内で float として使われる、または後退辺の配置が `F`」で、
入力が不動点の結果である。一方、内側ヘッドの採用は walk の途中で適用されるので、
不動点の結果は採用に依存する。§2.4 の下降はこの循環の現れである(§2.7 で確認)。

**分けた場合の形。** 巻き上げを不動点の前に「入口の仮定」として決め、不動点は
仮定を置いたヘッドから始める。採用が反復の外に出るので反復は純粋な上昇列になり、
収束後に「後退辺が仮定を満たす」ことを確かめる。満たさなければ仮定を外してやり直す。
この形は Array の種付け(`analyse_loop_head`、`merge.rs:587-616`)がすでに採っている。

**先に決めるための材料。** 不動点の前に使えるのは次の 2 つである。

- TraceIR に載っているインラインキャッシュのクラス(二項演算のオペランドが Float か)。
- `slot_analysis.rs` の def-use 表(ループ内の読みと定義。iseq ごとに 1 回作られ不変)。

「ループ内のすべての定義が Float を返す演算で、読みがすべて float 用途」のスロットを
候補にできる。IR を新設するなら、この 2 つを束ねたループ単位の要約が最小の形になる。

**リスク(既存の実測から)。**

- 型と用途だけで決めた採用集合は、不動点が選ぶ集合の上位集合になり、入口の unbox が
  増えて 2〜4% 退行した(`regalloc_separation.md` §16.4、§16.6)。逆に狭いと
  コピーで運ばれる float を落として 9% 退行した(§40)。現行の和集合(§40.2)は
  この 2 つの失敗の間に置かれている。事前の要約がこの集合を再現できるかが成否を分ける。
- §2.7 は逆向きの示唆も与える。現行は最外ヘッドで不要な採用をしており、
  それを外しても命令数は減った。事前に決める方式は「そのループの中で読まれるか」を
  def-use 表から直接見られるので、この過剰は避けやすい。
- 仮定が外れたときのやり直しは不動点 1 回ぶんのコストになる(Array の種付けと同じ)。

**位置づけ。** 方向として妥当で、G2(反復の性質を検査可能にする)に最も直接に効く。
ただし配置の選択に触れるので §13.4 のベンチゲートが要り、規模は中〜大である。
A・B の後、A′ で「join にしても退行しない」ことを両アーキで確かめてから着手するのが
安全である(A′ が通れば、採用を反復の外へ出しても後退辺の情報は足りている、という
傍証になる)。

#### §5.4 記録段階の結果(2026-11-13)

- **入れたもの。** `jit-log` 限定の `loop_float_candidates`(`loop_analysis.rs`)。
  ループ入口の合流(`merge.rs`、コード生成時だけ)で `keep_backedge_floats` の直後に、
  不動点を見ずに決めた候補集合を求め、合流が採用した集合(最内フレームで `F` または
  `Sf(_, Float)` のスロット)と比べて `FX54_*` に数える。`MONORUBY_FX54_LOG` を
  付けると、差のあるヘッドごとにスロットと候補から外れた理由を出す。生成コードには
  触れない。
- **候補の規則。** 使う材料はバイトコード、インラインキャッシュ、def-use 表、
  ループ入口に来た状態だけである。スロットが候補になる条件は次のとおり。
  - ループ内で float のオペランドとして読まれる(`BinOp` / `BinCmp` / `UnOp` で、
    キャッシュがそのオペランドを `Float` と言う)。
  - ループ先頭で生きている。def-use 表で生きていて、かつループ内のどこかの基本ブロックで
    書かれる前に読まれる。
  - どの入口も float に橋渡しできる(合流の `promotable` と同じ判定)。
  - ブロックリテラルが触らない。
  - ループ内の定義がすべて float である。数える定義は float 算術、float リテラル
    (`FrozenLiteral` を含む)、float の値のコピー、そして同じ基本ブロックの中で
    float として読まれる定義(`Index` や呼び出しの結果。その読みがガードになる)。
    定義が無い場合は、入口で `Float` か、クラスが未知(読みのガードを入口へ巻き上げられる)。
- **規則を詰める過程で分かったこと。** 最初の素朴な版(スロット単位で流れを見ない
  コピー追跡)は so_mandelbrot でほとんど一致しなかった。原因は次の 3 つだった。
  - 一時レジスタが用途をまたいで使い回される(`%22` が float 積、整数 2、比較結果を
    順に持つ)。コピーは基本ブロックの中で元をたどる必要がある。
  - `zr = 0.0` は `Literal` ではなく `FrozenLiteral` になる。

#### 死んだスロットを採用しない実験の結果(2026-11-13、不採用)

上の 1. を既定無効の feature で試した。`merge.rs` の採用 3 種(`adopt`、`adopt_sf`、
`adopt_deferred`)に「ループ先頭で生きている」を条件として足した。生きているかの判定は
2 通り試した。

- (a) 表の生存解析だけ。ヘッドの先頭で読まれるか、`table_live_after` が真。
- (b) (a) に加えて、ループのどこかの基本ブロックで書く前に読まれる。§5.4 の記録段階と同じ判定。

`jit-log` の記録では、(a) で so_nbody・matmul・spectral・lerp の死んだ採用が 0 になった。
so_mandelbrot は 24 から 12 に、accum は 2 から 1 に減った。
so_mandelbrot の残り 12 は、トップレベルの局所変数 `tr` `ti` である。ループの後の
読みはないが、表の解析では生きている扱いになる。(b) では両方とも 0 になった。

cachegrind の Ir(x86-64、現行の採用との差)は次のとおり。出力はすべて一致した。

| ベンチマーク | (a) 表の生存 | (b) 表 + 書く前の読み |
|---|---|---|
| mandelbrot (1000) | **+3.47%** | **+41.4%** |
| nbody (50k) | +0.03% | +0.05% |
| app_aobench | +0.05% | +0.04% |
| plb2/matmul 200 | +0.09% | +0.09% |
| optcarrot | −0.50% | −0.50% |

optcarrot では、jit-log の walk 数と JIT コードの総バイト数が変わらなかった。差は
コンパイラのバイナリ自体の違い(リリースビルドの配置)によるもので、採用の変化ではない。

**結論: 先頭で死んでいるスロットの `F` 採用は無駄ではない。** ヘッドが `S` のままだと、
後退辺で `F` → `S` の橋渡しが毎周 box する。死んでいるので値は誰も読まないのに box は
起きる。`F` で採用すれば、それが無くなる。これは `merge.rs` の注記にある
「採用集合を配置より狭めると mandelbrot が退行する」と同じ現象である。
§2.7 の「入口の unbox が無駄」という評価は、この後退辺の box を勘定に入れていなかった。
採用を止めるのではなく、次の形にすれば両方を省ける。

- 死んだスロットは、ヘッドで「表現を問わない」ものとする。
- 後退辺では書き戻さず、入口でも unbox しない。

これは連結(link)の側の変更で、§5.4 とは別の手順になる。実験の差分は
`/mnt/project-files/patches/fixpoint_engine_2026-11-13/skip_dead_experiment.patch` にある。

#### ブロックの要約の結果(2026-11-13、記録のみ)

上の 2. の前提になる部品を作った。生成コードは変えていない(`jit-log` のみ)。

- **要約の中身。** ブロックの iseq 1 つについて、外側のフレームのスロットごとに次を持つ
  (`BlockSummary`、`loop_analysis.rs`)。
  - float のオペランドとして読むか。
  - ブロックのどこかの基本ブロックで、書く前に読むか。
  - 書き込みごとに、入れる値が float か、別の外側スロットのコピーか、それ以外か。

  ブロックは 0 回でも何回でも走りうるので、どれも「かもしれない」である。
  ブロックの書き込みは、スロットがそれまで持っていた値を殺さない。
  入れ子のブロックは、深さを 1 つ増やして同じ要約を作り、呼び出しの位置で合成する。
- **使い方。** `loop_float_candidates` は、ループ内のブロック付き呼び出しを
  「要約どおりに読み書きする命令」として扱う。「ブロックが触るスロットは候補にしない」
  という規則は外した。残した例外は 1 つで、ブロックが不透明な場合である
  (ハンドラを持つ、lambda を含む、フレームを捕まえうる呼び出しを含む)。
- **詰める過程で分かったこと。**
  - ループの外にあるブロックは見なくてよい。ループの前の `call_block { x = n * 1.5 }` が
    `x` に触っていても、不動点は `x` を採用している。ブロックが Proc として逃げたときは
    捕獲ガードで脱出するので、JIT コードの中では起きない。
  - 呼び出し先が組み込み(Rust 実装の `sort_by` など)のとき、ブロックはこの単位に
    コンパイルされず、フレーム経由で読み書きする。この場合、ブロックの float 読みは
    数えず、書き込みは「クラス不明の値」として扱うと、不動点と一致した。
    判定は呼び出し位置だけで決まる部分(Ruby のメソッドに解決済みで、`&blk` で
    受けない)だけを使った。特殊化スタックや dispatch arm の条件は見ていない。
- **ブロック入りの小品 4 本の結果**(float の局所変数をブロックが読み書きする `while` ループ。
  `/mnt/project-files/patches/fixpoint_engine_2026-11-13/fx54_block_samples/`)。

#### float リテラルの初期値を保持する試作(2026-11-13、既定で無効のフィーチャ `carry-float-literal`)

上の 1. を調べた。足りなかったのは不動点の側ではなく、呼び出し位置の 1 か所だった。

- **原因。** 外側の float を呼び出し先のループ越しに保持する仕組みは、すでにある。
  ブロックを渡す呼び出しの直前で、レジスタにある float を持ち主のスピル領域へ移し
  (`write_back` の `Keep::Claims`)、ブロックの書き込みはその場所への生の f64 の
  書き込みになる(stage 1'')。ただし初期値が float リテラルのとき(`s = 0.0`)、
  スロットは定数 `C(0.0)` のまま呼び出しに入る。ループのヘッドは
  「入口 `C(0.0)`」と「後退辺のブロックの書き込み」を合流して `S` にする。
  `s = arr[0] * 2.0` のように計算した float で始めると、同じブロックで保持される
  (Ir 2,334M が 1,637M になる)。
- **試作。** ブロックをインラインする呼び出しの直前で、ブロックの要約を見る。
  ブロックが float として読み、書き込みがすべて float であるスロットが、
  持ち主のフレームで float リテラルなら、`F` にする(定数をロードする 1 命令)。
  あとは既存の経路がそのまま働く。変更は `method_call.rs` の呼び出し位置と、
  `SlotState::float_literal_to_F`、`JitContext::block_float_accumulators` である。
  要約は得かどうかの判断にだけ使う。ブロックが実際に何をしても、呼び出し位置が
  立てる主張は「計算した float」が今も立てているものと同じなので、
  健全性は要約に依存しない。

## 6. 着手順の推奨

全面的な SSA 化は後回しとする(2026-11-12 の判断)。その前提での順である。
前半(1〜3)は生成コードを変えない。後半(4〜7)はベンチゲート
(`regalloc_separation.md` §13.4)が要る。

| 順 | 手順 | 内容と理由 | 規模 | 生成コード |
|---|---|---|---|---|
| 1 | **A** 上限の是正と abort の解消 | 現に落ちるバグなので最優先。上限を鎖の長さから導き、超過は `CompileError`。§2.3 の 5 本を回帰テストに。着手前に `CompileError` の後始末(入れ子の特殊化、ループ JIT)を確認する | 小 | 不変 |
| 2 | **B** 計測の常設 | 以降の判断材料。§7 の差分がほぼそのまま使える | 小 | 不変 |
| 3 | **E** `LinkMode` 段の整合テスト | 1・2 と並行でよい。4 で join を変える前に現状の性質を固定する | 小 | 不変 |
| 4 | **A′** 後退辺を join で蓄積 | 省略オブジェクトの突き合わせを足し、mandelbrot / nbody / matmul / optcarrot を両アーキで A/B。通れば後退辺が構成上の上昇列になり、1 の上限が証明できる値になる | 小〜中 | 変わる |
| 5 | **D** 入口一致 walk の省略 | 先に C の決定性 shadow(debug では省略せず実行して突き合わせ)を入れる。aobench と optcarrot で walk の 2〜3 割が対象 | 中 | 不変のはず |
| 6 | **§5.4** 巻き上げと不動点の分離 | 4 が通っていることが前提。コード生成はスロットのまま、TraceIR と def-use 表から採用候補を事前に決める。最初は現行の採用集合との差を記録するだけの段階を挟む | 中〜大 | 変わる |
| 7 | **F** 束の要素追加の試行 | `join_profile` で最初の要素を決める。高さを定数として公開し、1 の上限式と 3 のテストに参照させる | 大 | 変わる |

補足:

- **C の扱い。** 決定性の shadow は 5 の前提として残す。「更新の向き」の記録は
  2 の計測に含め、4 を採れば assert にする必要は無くなる。4 を採らない場合だけ、
  C の 2(向きの不変条件)を 5 の前に行う。
- **区切り。** 1〜3 で abort が消え、数値が取れ、性質がテストで固定される。
  4〜5 で停止性が構成で保証され、コンパイル時間が減る。6 以降は設計の整理と
  束の細分化で、実機のベンチが律速になる。
- **見送るもの。** インライン生成器への型シグネチャ別登録(§5.2)、
  「動いたスロットだけ widen して再 walk」(A の項)、
  「変化したヘッドを含むループだけ再 walk」(D の項)、全面的な SSA 化。

残っている判断:

1. A の上限超過時を「コンパイル断念(`CompileError`)」とするか、鎖の長さぶん
   回し切ることだけにして超過は debug の panic に残すか。推奨は前者。
2. F で最初に足す要素。`join_profile` の実測で決めるのがよいが、候補があれば
   それを優先する。
